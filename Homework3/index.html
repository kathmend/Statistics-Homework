Caesar Cipher and Toy ECC

A simple comparison of encryption, decryption, key recovery and statistical attacks.

1. INTRODUCTION

Two ways to hide a message

The Caesar cipher shifts letters using one secret number. Our toy elliptic-curve scheme uses a public key and curve-point arithmetic to encrypt the same message.

This homework extends the elliptic-curve concepts introduced in previous assignments by implementing a toy EC ElGamal encryption scheme on secp256k1 and comparing it with the Caesar cipher.

EXPERIMENT B

Toy EC ElGamal encryption (secp256k1)

We use the real secp256k1 curve, but deliberately limit the receiver private key to 1–256. Each UTF-8 byte b is mapped to a curve point M = (b + 1)G. We choose a new temporary scalar r from 1–128 for each byte, then encrypt with C1 = rG and C2 = M + rQ. This is a simplified teaching construction, not secure encryption.

6. DISCUSSION

Why do these attacks work?

01

Caesar: statistical weakness

Shifting letters preserves their relative frequencies. English frequency analysis can suggest the shift, especially for longer natural texts.

02

Caesar: tiny key space

Trying all 26 shifts is easy, even when frequency analysis fails. The best-looking result may still require human interpretation.

03

ECC: restricted private keys

Our public key can be matched against just 256 candidates. The temporary scalar also has only 128 possible values per byte. These restrictions are choices of this toy design, not properties of secp256k1.

04

Real ECC is different

A properly generated secp256k1 private key is selected from an enormous space (roughly 2²⁵⁶ values). Exhaustive search is not practical.

Limitations of our toy design

We use direct point-message EC ElGamal on secp256k1, not Ethereum transaction encryption. Every UTF-8 byte is encoded as one of 256 known points M = (b + 1)G. Both the receiver key (1–256) and the per-byte temporary scalar (1–128) are deliberately restricted. An attacker can enumerate the receiver key from Q or the temporary scalar from C1. These are separate weaknesses; a secure real-world scheme needs properly generated keys and reviewed authenticated encryption.
